# Recovered device catch-up and navigation

Owner follow-up November 8, tracked in #22. A fresh PWA install authorizes a new device key and restores historical keys. Server history queues detect missing recipient packets for the new device. Previously this caused the unlocked author to re-encrypt their posts and attachments even when recovery already gave that device access.

The shared client now skips a candidate only if the current server-computed audience has missing devices exclusively belonging to this author, a recovered key matches the original envelope, and recovered keys also cover each attachment. The API must also confirm that every eligible peer device/member already has its server-side grant. Missing/unknown coverage never skips catch-up, including mixed own-device and reconnect/grant-repair cases. Missing peer devices, absent recovered keys, or candidates with no missing packet (possible recipient-table repair) continue through the existing catch-up workflow. This changes neither audience authorization nor signed-envelope validation. No server read grants are added by skipping. Other clients retain their existing behavior.

Post and photo candidate scanning advances through every page, including pages with failed items. Undelivered items remain in the server queue and return on later scans; one broken item cannot pin the cursor. Standalone photos cache verified media coverage for the current grant/epoch, avoiding repeat media downloads. A real peer gap still triggers preparation and the existing exact-recipient, current-policy, revision and expiry validation. This is not a redesign of per-device encryption: it eliminates unnecessary author-side copies when recovery already covers them.

Failures automatically retry while the authorized author device is unlocked, online and visible. Per-item exponential backoff starts at five seconds and caps at five minutes; the twenty-second foreground poll and focus/online events drive checks. Retries have no attempt limit. A nonblocking delayed-access notice explains that retries are automatic; there is no retry button. Persistent history writes retain unload and signout protection, but do not lock navigation between member routes that retain the unlocked vault. Navigation that leaves that vault still waits; foreground saves retain their existing navigation guard. An unconfirmed response is read back first. If the exact candidate is committed, no resubmission occurs. If the source is unchanged, retry the same prepared ciphertext/media IDs. A changed source retires the stale candidate; a known rejection plus an unchanged read discards unattached replacements before preparing from a fresh audience. Offline/hidden suspension stops reads/preparation without treating it as a permanent failure. Submitted writes are allowed to settle; navigation remains available. No retry changes recipient eligibility, history consent or expiry.

The default native shells use this shared implementation. Legacy Swift fallback behavior is unchanged. Physical startup and storage checks remain #49/#114. Automated checks cover recovered/self versus peer gaps, missing attachment keys, foreground/background navigation, and existing post refresh reconciliation; hosted release checks must confirm zero post/media refresh writes for a recovered own-device-only gap.
