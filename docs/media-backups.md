# Private ciphertext media snapshots

Database backups do not contain photo bytes. Migration 033 and `media-backup.ts` add a daily private R2 snapshot paired with a PostgreSQL restore timestamp. The feature is implemented and locally tested, but remains disabled in unprovisioned environments. It is a launch requirement for staging/production readiness, not a reason to describe hosted recovery as verified before a real PlanetScale/R2 drill.

## Provisioning and first snapshot

Verify the chosen PlanetScale database's exact timestamp restore procedure and configure at least seven days of backup/PITR retention for both staging and production. `scripts/provision-media-backup.py staging|production --verified-pitr-days 7` records an operator's verified retention policy; it does not inspect PlanetScale or upgrade a plan. A new database has only the history actually recorded so far: before each restore, verify that the selected media snapshot's exact paired timestamp lies inside the provider's available PITR window. Run provisioning with the private credential loader only after policy verification and after real Hyperdrive IDs exist. It creates a distinct `porchday-{environment}-media-backup` bucket, disables its managed public domain, refuses any custom domains, installs and verifies a seven-day lifecycle rule, then records the binding in `infra/resources.json`. No backup setup script has been run against the real hosted environment yet.

Apply all migrations, including 033 for snapshot metadata and 036 for raw upload digests, and render the environment using `scripts/configure-worker.py`. The renderer defaults `MEDIA_BACKUP_ENABLED` to false. Enabling requires a separate backup bucket and the recorded retention policy. The optional `MEDIA_BACKUP` binding must never refer to live `MEDIA` or `RECOVERY_JOURNAL`. The independent journal has no seven-day lifecycle and must outlive every retained database/media snapshot.

The daily `17 3 * * *` cron enqueues a backup-start message. The minute-by-minute expiry cron remains separate. Startup and copy failures retry through the existing queue and dead-letter policy; no HTTP route starts a backup or grants access to one. `/health` remains a deployment smoke check, while protected operational health reports missing configuration, missing baseline, old restore points, failed runs, or stuck copies. Keep real-member admission closed until the first complete snapshot and a reviewed restore drill exist.

## Snapshot mechanics

The jobs identity first obtains the PostgreSQL UTC timestamp in a separate statement, before freezing the current live ready/attached media inventory in SQL. The frozen rows contain only object paths, canonical envelope and raw-byte digests, and byte counts. No R2 I/O occurs while SQL transaction locks are held. Media is immutable after its validated upload; edits and reshares create new object IDs.

The copy process reads that database inventory, never arbitrary bucket contents. A queue message copies at most eight objects sequentially and publishes an immutable manifest page. Native R2 conditional writes claim a short lease and advance the cursor; retried or concurrently delivered messages cannot advance it twice. State, immutable pages, ciphertext copies and the final completion marker are under `snapshots/{UUID}/`. Pages form a SHA-256 linked chain. The verifier follows a strictly decreasing page index, with exact expected keys and globally ordered object paths, keeping page and object memory bounded.

There are two different digests. PostgreSQL authenticates the canonical JSON representation of an envelope, while uploaded JSON bytes may have a different field order or whitespace. Successful upload atomically stores a separate raw-byte SHA-256 with the ready state after checking the canonical reservation binding. Copying streams bytes through native R2 checksum verification and incremental SHA-256; it never parses or canonicalizes the full object. Manifests record both digests. Restoring checks raw-byte integrity and both surviving database digests and byte size. Missing raw digests on old draft fixtures fail backup/release closed; they are not silently inferred or trusted. No step decrypts the OpenPGP content or obtains a member key.

An object that disappears during copying may be omitted only when its exact path has a database deletion-outbox proof. Before writing the completion marker, the copier flushes the independent privacy journal and requires coverage of every omission proof. An unexplained missing object, digest mismatch, failed write, changed database generation or expired snapshot fails the run. The completion marker is written last. An incomplete snapshot is unusable.

The paired timestamp precedes the inventory scan: newly uploaded objects may be harmless extras, and objects deleted between the timestamp and inventory capture are handled by the latest independent privacy journal. Restore must use the exact paired timestamp, reconcile the latest privacy decisions, and verify that every still-required media row is covered. Never substitute an arbitrary newer database snapshot.

## Retention and access

The logical restore window ends exactly seven days after the paired timestamp. Both verifier and operator copy endpoint reject expired snapshots even if bytes remain in storage. The lifecycle deletes objects seven days after each object's upload; physical removal is asynchronous and can lag. Cloudflare says removal typically occurs within 24 hours of expiration, and can take longer. This is not an instantaneous erasure promise. [Cloudflare object lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)

Snapshot paths and routing metadata are sensitive even though photo contents remain encrypted. No public domains, member routes, staff browsing routes or plaintext previews expose the backup bucket. Production persisted application logs remain disabled; operational counters contain no object paths or member IDs. The present policy retains full daily ciphertext copies, so storage approaches seven times live media plus page metadata. Each source object incurs copy reads/writes daily; measure cost and duration before extending beyond pilot scale. Backups are in a different bucket in the same Cloudflare account, which does not protect against loss of the entire account.

## Restore a completed snapshot

1. Follow `docs/restore-safety.md`: quarantine the independent journal, stop traffic/jobs, resolve pending intents, verify its complete chain, and restore PostgreSQL to the exact `run.restore_at` from the selected unexpired media manifest. Retain the provider's restore evidence. The operator input is an attestation of the actual provider restore point, not an automated PlanetScale check.
2. Run `restore-safety.ts replay`. This removes obsolete rows, applies latest deadlines/revisions/revocations, invalidates restored capabilities and deletes forbidden media paths. Quarantine remains active.
3. Set `MEDIA_BACKUP_BUCKET`, `MEDIA_BUCKET`, `MEDIA_RESTORE_SNAPSHOT_ID` and `MEDIA_RESTORE_PITR_AT` in the private operator environment; the timestamp must exactly match the manifest's canonical UTC value. Run `npx tsx scripts/restore-safety.ts restore-media` through the credential loader. No secret belongs in shell arguments or source files.
4. The command requires both the database and independent journal to be quarantined at the same reconciled cursor. It verifies every manifest page and raw object hash, then restores only objects still required by live database rows. Deleted/expired objects are skipped; an omitted object that is still required causes failure. A reserved database connection holds a temporary verified-key table, populated incrementally; an anti-join detects any required object missing from the snapshot. No array of all member object paths is sent to SQL.
5. The short-lived operator Worker performs create-only native R2 copies and rejects conflicting existing bytes, missing/incomplete/expired snapshots, wrong sizes and wrong raw hashes. It receives no member decryption keys. The endpoint is removed and its absence verified; its bearer also expires after one hour if the operator process crashes.
6. Perform the application and security checks in the restore runbook. Set the reviewed journal sequence and run `release`. Release now streams every still-required live media object in bounded pages and verifies its byte size and the raw digest committed with its validated upload before clearing quarantine. Skipping `restore-media`, a failed copy, or a missing/changed live object cannot pass release. A database with no required media can initialize/release without a media verification callback.

All failures keep quarantine in place. Missing live media is an availability failure, not permission to drop the member's surviving media row or invent a replacement. The release verifier does not silently repair bytes.

## Evidence

Native Miniflare R2 tests cover bounded pages, concurrent message claims, interrupted manifest writes, idempotent copy, unexplained missing data, journal-covered omissions, manifest/object tampering, wrong restore time and expiry. Operator Worker tests cover short-lived authorization, read-only scope, conditional copy, collision refusal and raw digest verification, including rejection of a different canonical digest for the same JSON object.

`npx tsx scripts/drill-restore-local.ts --run` creates real OpenPGP photos through the actual HTTP reservation/upload routes. It explicitly confirms their raw byte hash differs from the database canonical digest, then runs the production copy/manifest code, an actual `pg_dump`/`pg_restore` into an isolated database, reopened native R2 persistence, latest journal reconciliation, and the shared operator media restore algorithm. It proves that deleted media is not recopied, missing/failed release verification blocks reopening, and surviving ciphertext decrypts after verified release. The local run passed on October 25, 2026. A real hosted PlanetScale snapshot and production R2 restore remain an external deployment verification requirement.

`npx tsx scripts/probe-media-workerd.ts --run` executes the actual backup and operator code inside local workerd with native R2, using real signed OpenPGP ciphertext padded with valid JSON whitespace to the full 22,020,096-byte upload bound. The October 25 probe first exposed whole-JSON canonicalization using approximately 271 MB of sampled heap plus backing storage. Streaming raw checksum verification reduced the copy sample to approximately 16.3 MB and the entire backup/operator verification/restore sequence to approximately 32.6 MB in a fresh isolate. CDP samples can miss transient peaks and are not a production memory certification. The same local runtime accepted a retained 160 MiB allocation: it does **not** enforce Cloudflare's deployed [128 MB per-isolate limit](https://developers.cloudflare.com/workers/platform/limits/#memory). The optional `--upload` also creates a disposable local PostgreSQL database and measures the actual POST/PUT upload handlers; runtime access uses the social database role and real RLS. These probe-only handlers are never deployed.

The `--copies=8` variant exercises a full sequential page with eight synthetic copies of those maximum-size encrypted bytes (176,160,768 bytes total). On workerd 1.20261019.1 and Miniflare 5.20261019.2-beta, copying took 1.5 seconds, with approximately 18.0 MB sampled heap plus backing after copying and 20.5 MB across the subsequent verification/restore sequence. These are sampled local observations, not enforced memory bounds or a load/concurrency certification. Maximum upload-handler memory is a separate check; successful streaming backup tests do not establish upload safety.

Native R2 consistency and conditional writes are the basis for cursor publication; ordinary object REST conditional writes were independently probed and are not used for this purpose. [Cloudflare R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/), [Workers R2 API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)
