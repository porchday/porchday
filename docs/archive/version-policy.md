# Portable archive version policy

`format: "porchday-archive"` identifies this local portable representation, and integer `version: 1` identifies its compatibility contract. Neither is the server API version, the server export-page `schema_version`, the OpenPGP packet version, nor the signed service envelope's `v` field. Do not select a decoder by filename alone or conflate these version spaces.

The checked-in [v1 JSON Schema](archive-v1.schema.json), [container specification](README.md), [interfaces](importer.ts), and synthetic samples travel with the source release. There is no remote schema fetch requirement. An importer must reject unknown format/version pairs before attempting writes and offer to keep the untouched file. A future version must have a separate schema, fixtures and explicit conversion rules; do not silently reinterpret a version 2 file as version 1.

Within v1, corrections that clarify existing behavior and optional additive data fields are compatible changes. Readers may retain unknown JSON fields as inert data, report unsupported fields in preview, and ignore them for destination behavior. They must not execute them, grant privileges from them, infer broader audiences, or discard them from a claimed lossless conversion without disclosure. Current clients preserve many unknown payload fields but do not promise to import every unknown top-level field. The schema therefore permits additional fields; passing the schema is not permission to transmit them indiscriminately.

Renaming/removing required fields, changing their meaning/type, introducing a required feature older readers cannot safely interpret, changing expiry/audience semantics, or changing multipart completeness rules requires a new integer version. A new media type or encryption/container requirement that existing clients cannot read needs an explicit compatibility design and version change; it must not be disguised as a JPEG v1 archive. Safety fixes may reject malformed files previously tolerated without changing the valid v1 format.

There is no `minor_version` field in the current format, no automatic remote schema update and no promised third-party support period. A release that changes behavior must update these docs, a representative valid fixture, and rejection/compatibility tests. Breaking-version work must document which prior versions are readable and how conversion preserves original deadlines, provenance, private import defaults and unknown fields. Do not remove a reader without announcing the migration path before that release.

The original standalone ZIP without `archive_set` remains supported. The existing streaming multipart form is also v1; canonical exporters write unknown totals until the final completion part. A single-part export may still use `archive_set` with `index: 1`, `total: 1`, `complete: true`. Do not split, concatenate, or reassign an existing set's identities without deliberately creating a new complete set and revalidating references.

This policy and its sample are versioned with the source. Their availability does not establish an external support promise or guarantee compatibility with another platform.
