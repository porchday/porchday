# Porchday operations

## Admission and launch gates

Registration requires an email-bound, expiring invitation issued by an operator or eligible member, adult attestation, accepted community rules, and verified email. `SIGNUP_ENABLED` is a deliberate deployment gate. The owner has authorized production access and explicitly requested that production invited signup remain enabled. Both environments therefore persist `signup_enabled=true`; preserve production's setting unless the owner requests that it be disabled. This authorization covers owner use and does not remove the encryption review, support staffing, nonprofit/legal disclosures and other admission requirements for a broader launch. Synthetic test accounts are operational test identities, not autonomous social participants.

Original source is licensed under Apache-2.0. Source publication does not authorize deployment, grant production access or remove the broader service admission requirements. See the [publication record](open-source-readiness.md) for source-release checks.

## Secrets and roles

Deployment credentials stay outside Git at `~/.config/inner-circle/secrets.env` (0600). Use `python3 scripts/with-secrets.py COMMAND` only for trusted deployment commands. Never run an arbitrary downloaded script with that environment. Database migration access is distinct from runtime auth/social/jobs roles. Runtime roles are not owners or BYPASSRLS roles. Hyperdrive query caching must be disabled for all three bindings.

A normal login password or a support-led password reset cannot decrypt old private content. Members need a trusted device or their content recovery secret. Operators have no content master key.

## Environments

Staging and production have distinct Cloudflare R2 buckets and queues listed in `infra/resources.json`. Their databases, runtime roles, auth secrets and Hyperdrive connections must also be separate. R2 managed public domains are explicitly disabled. Preview deployments may not use production data.

## Photo uploads

Encrypted media uploads are limited to 22,020,096 bytes. The authenticated media routes count streamed bytes even when `Content-Length` is absent or incorrect. Uploads use private, create-only pending R2 objects; only validated uploads become readable. Finalization rechecks ownership, account state, reservation state and expiry. Cleanup after an ambiguous database commit must not delete an object that reached ready/attached state.

Large envelope parsing and hashing use one nonwaiting permit per Worker isolate. Overlapping work returns `429 MEDIA_BUSY` with `Retry-After: 1`; the clients retain the draft and selected photos, and a manual retry creates fresh upload identities. This is a resource guard, not a load-test result. The pinned `@streamparser/json` dependency has a local bounded accumulator adapter for Unicode preservation and allocation limits; keep its differential JSON/UTF-8 regressions when upgrading. See `docs/media-upload-memory.md` for the implementation constraints and measured evidence; production throughput requires separate load testing.

## Deletion and expiry

Reads deny expired data immediately, even when jobs are offline. Cron enqueues expiry work. The queue consumer deletes expired metadata and retries ciphertext deletion through a durable PostgreSQL outbox. Every queue run is idempotent; completed R2 deletions can be retried safely. Identity deletion has a separate outbox so a transient auth-database failure cannot leave a deleted member usable.

Use the [queue reconciliation and bounded DLQ replay procedure](queue-recovery.md) after resolving an actual consumer failure. Queue acknowledgements never substitute for durable outbox completion.

Media cleanup deletes bytes immediately, then performs another deletion after the outbox entry is at least ten minutes old before marking it complete. This catches a pending writer that finishes after the first delete and crashes before its own cleanup. Uploads have a two-minute deadline; the delayed pass does not extend authorization or content expiry. Storage errors retain the outbox entry for retry.

Migration 041 records `first_deleted_at` only after R2 acknowledges a successful deletion and the database update commits. An attempt or claim lease is not proof of success. A crash or failed database acknowledgement leaves the first pass unconfirmed; another idempotent delete must establish it. The first successful timestamp is retained on later retries. Health version 2 warns if the unconfirmed first pass is more than 600 seconds old, or if a confirmed first pass still lacks final completion more than 900 seconds after the original outbox creation. The final pass is eligible at 600 seconds; its five-minute completion allowance matches the design's fifteen-minute primary-storage cleanup target. The independent cleanup-heartbeat warning remains 180 seconds. Neither a lease nor a retry/backoff timestamp moves these obligations, and completed entries are excluded.

Apply migration 041 before deploying the new Worker. It preserves `app.operational_snapshot()` for older Workers and adds the strictly validated `app.operational_snapshot_v2()` for the new release. Missing, old or unknown version-2 output fails the protected health request rather than guessing success. Existing rows receive no invented first-pass timestamp; an older concurrent Worker may complete cleanup, but its unrecorded initial pass stays conservatively unconfirmed until a new Worker acknowledges another deletion. Runtime jobs can read the new aggregate function; member roles cannot. Do not backfill from `attempts`, force a queue, or move timestamps to silence an alert.

This corrects a verified scheduling false alarm: on October 25, one staging outbox entry became final-pass eligible at 18:05:59.235 UTC and completed naturally at 18:07:50.759 UTC, 712 seconds after creation. The old alert fired immediately after the required ten-minute floor even though completion was within the documented fifteen-minute target. Read-only follow-up at 18:08:49 UTC found no pending media work and a twelve-second cleanup heartbeat. The change does not weaken immediate read denial or the delayed deletion itself.

During restoration, apply deletion-ledger decisions and expiration before resuming member traffic. A completed database restore alone is not a successful media restore. The [isolated hosted staging drill](hosted-restore-drill.md#second-hosted-attempt-verified-and-cleaned-up) passed database/media recovery, independent deletion and expiry replay, restricted-role release and original-key decryption on October 25, 2026. Its measured result is evidence for that coordinated cut, not an availability or recovery-time guarantee. Retain the provisional 24-hour RPO/8-hour RTO objectives and repeat the drill quarterly and after relevant recovery changes.

Owner development access (October 25, 2026): invited signup was enabled on staging at the owner’s request to play with Porchday during development. A seven-day invitation was issued for the owner’s Gmail address. Production admission was closed at that checkpoint. The owner subsequently authorized their own production account and requested that production invited signup stay enabled. Both environment settings now persist that policy in `infra/resources.json`; the latest runtime verification belongs in the [build record](build-status.md).

Member invitations: Connections → Invite someone accepts one email address. Active, verified members can request ten invitations per rolling 24 hours; each recipient has a seven-day issuance cooldown. The API's generic 202 response acknowledges the request without disclosing whether an account exists or proving delivery. Codes are single-use and bound to the recipient email. They do not create a friendship. The signup and social-invitation pause settings gate the feature. Account/recovery mail is prioritized over invitation mail. Invitation payloads remain encrypted in the outbox until delivery or their exact seven-day deadline, with retry backoff capped at six hours. Sender deletion invalidates invitations; seven-day keyed recipient cooldown metadata retains no deleted sender identity. The operator CLI continues to save a private invitation link without sending mail.

Before deploying from parallel work, compare the current provider version and settings with the saved configuration. Stop on unexpected changes before uploading; do not rely solely on a comparison after deployment. Preserve `environments.staging.signup_enabled=true` and `environments.production.signup_enabled=true`. Do not disable production signup after issuing the owner's invitation or during later deployments unless the owner requests it. A code-only rollout must not silently undo another authorized session's signup setting or invitation-link fix.

## Email and monitoring

Cloudflare Email Sending is enabled for porchday.com with SPF, DKIM and DMARC. Email body previews were disabled through the API to avoid retaining password-reset links in activity previews. Account emails omit private social content. Delivered-email acceptance passed for the three original synthetic signups, ordinary password reset, stolen-account recovery and two-address email change; the owner also confirmed the recovery and email-change security notices. Member-invitation delivery, code prefill, recipient signup, email verification and login passed; [recipient acceptance](member-invitations-and-sharing.md) combines human confirmation with read-only account/invitation checks. Bounce handling remains unverified. The owner confirmed both staging availability attention and recovery emails after the monitor compatibility failure described in the [monitoring record](independent-monitoring.md).

Verification, reset, account-change and recovery messages enter a durable encrypted outbox in the same transaction as their associated change. Provider delivery starts after commit; failed attempts retry with bounded leases/backoff and a 30-minute queue lifetime. This delivery deadline is separate from action-link expiry: ordinary email-verification and email-change tokens currently last one hour. Delivery is at least once: a crash after provider acceptance but before acknowledgement can duplicate an email, while its action link remains single-use. Member deletion removes queued member mail. Recovery-case mail works without assuming account ownership and can notify a contact during a security hold. Superseded recovery contact/restore links are removed from the pending queue. Case deletion/retention cleanup removes its pending mail. This is server-side encryption of operational email, separate from client-only content encryption.

Application telemetry is restricted to fixed event/code/environment labels, normalized routes, numeric status/duration/count fields. The application never intentionally logs raw paths, bodies, auth cookies, tokens, member IDs or SQL details. Telemetry exceptions cannot block account or cleanup operations. Staging/production configuration disables application Workers Logs, tracing and Logpush: disabling invocation logs alone does not prove that provider-enriched console/error records omit sensitive request metadata. Cloudflare aggregate metrics and the separate health monitor remain available. Do not enable application logs, tail consumers, real-time tails or issue collection for real-member traffic until the exact output has been verified with synthetic token URLs and a reviewed redaction/retention design. This does not claim to disable Cloudflare's own security/edge records. [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) documents invocation metadata and the separate console/error records; [Workers metrics](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/) describes aggregate monitoring. Staging availability alert/recovery inbox delivery is verified. Telemetry-loss/performance notifications, bounce handling, provider security/edge retention and cost review remain separate operational checks.

The optional `METRICS` binding writes explicit bounded points directly to Cloudflare Analytics Engine, without request log enrichment. Its source redaction, weighted queries, retention and cost controls are described in `docs/operational-metrics.md`. An isolated synthetic provider probe first verified ingestion and queries; both deployed applications now emit live aggregate telemetry, and their dedicated-reader monitors report metrics readiness. `python3 scripts/with-secrets.py npx tsx scripts/probe-metrics-cloud.ts --run` repeats that check using an isolated dataset and a temporary authenticated Worker with a ten-minute capability. It has no database, media or member access; it verifies teardown and never prints its capability. Dataset rows are synthetic and remain under provider retention. Ingestion can take over 30 seconds, so an immediate empty query is not proof of a broken writer. Explicitly verify telemetry freshness and alert consumers before relying on these metrics for the pilot.

Both applications now include fixed journal/cleanup failure-phase codes. They identify where an operation stopped without recording raw errors or changing retry, acknowledgement or quarantine behavior. A phase code does not establish rollback or authorize clearing an unresolved privacy intent. See the [earlier staging incident](staging-privacy-incident-2026-10-25.md), [production interruption and verified recovery](build-status.md#production-login-interruption), and [environment-bound operator procedure](restore-safety.md#recovering-an-interrupted-operation-on-the-original-database). HTTP privacy operations now retain completion work through the Worker's bounded disconnect grace period while still awaiting durability before success; this does not make unknown outcomes safe to retry or clear automatically.

The separate monitor implements five-minute latency/error and telemetry-freshness checks in addition to minute availability probes. Both environments are already configured with dedicated account-scoped Analytics Engine read tokens and produce operational/metrics-ready observations. For a new deployment or deliberate reconfiguration, use `python3 scripts/configure-monitor.py staging --enable-metrics` (and the production equivalent) and `scripts/upload-monitor-secrets.py`; never install the broad deployment token in the monitor. Disabled or failed metric checks are explicitly unavailable/not configured and cannot establish a healthy metrics pipeline. The shipped SQL/parser have been exercised against isolated and live datasets. The owner confirmed the staging availability attention/recovery pair after a monitor runtime compatibility failure while direct application health remained healthy; that does not establish deliberate application-outage or telemetry/performance alert delivery. Those additional delivery checks remain admission work. See `docs/independent-monitoring.md` for sample floors, thresholds, retries, and platform-outage limitations.

`/health` proves only that the Worker can answer. `/api/operations/health` requires a separate environment-specific `OPERATIONS_HEALTH_TOKEN`, then checks the independent restore checkpoint and database. It returns only aggregate job/email counts and fixed issue codes. It reports a missing/older-than-three-minute cleanup heartbeat, an unconfirmed media-deletion first pass older than ten minutes or unfinished final pass older than fifteen minutes from creation, identity deletion older than five minutes, and queued email older than five minutes or exhausted delivery attempts. Only the jobs database role can read these aggregates or record a successful cleanup heartbeat. This token grants no member, staff or content access. Configure the independent monitor and verify alert delivery before admitting members.

Protected staging/production readiness also requires configured encrypted media backups and at least one completed snapshot. It flags a paired database restore point older than 26 hours, a retained unfinished copy older than two hours, and unfinished runs that have failed copy attempts. These are monitoring thresholds, not proof of the 24-hour RPO target. Readiness stays degraded during initial provisioning until the first complete baseline; `/health` remains available for basic deployment smoke checks. A recent media snapshot does not by itself prove provider database PITR availability or a successful hosted restore.

Migration 042 adds `operational_snapshot_v3()` while preserving v1/v2 for rollback. Deploy the migration before the new application. The strict v3 reader rejects older or unknown output. Jobs-only aggregates include unresolved moderation reports/appeals and verified, unresolved recovery cases, excluding expired retention and unverified contact reports. Review age starts at original report creation or verified contact, not assignment/update time. A provisional 24-hour oldest-item threshold raises a fixed backlog issue; it is an escalation policy, not a staffed support promise. The monitor receives counts/ages through its protected capability, never SQL credentials, case IDs, evidence or addresses. Actual reviewer staffing remains an admission gate. See [database/storage visibility](database-capacity.md) for provider capacity checks.

## Incident handling

See [incident response](incident-response.md) for persistent per-environment posting/upload/invitation pauses, deployment and recovery checks, compromised credentials, storage failures, lost administrator access, abuse surges and mistaken moderation. These selective controls preserve authorized reads and account safety actions; they are not a substitute for full privacy quarantine or a tested key-rotation procedure.

For suspected takeover, an unverified report never freezes or transfers an account. Verify the claimant's safe contact, then have authorized staff review corroborating evidence. A confirmed hold must revoke all login sessions and integration grants, block export/deletion/credential changes, preserve recovery and appeals, and keep ordinary content timers expiring. Recovery of account ownership cannot recover missing encryption keys. Two distinct authorized reviewers are required where trusted methods are lost.

Staff workflow code is implemented and covered by local tests. Cloudflare Access applications require independent security-key/biometric MFA and one-hour sessions; the staging roster has the two approved people, while production remains owner-only. Provider reads verify their configuration. ## Account security and staff access

Configure `STAFF_ACCESS_ISSUER` to the exact HTTPS Cloudflare Access team origin and `STAFF_ACCESS_AUDIENCE` to the staff application's audience. The origin checks the assertion even on alternate origins. Access alone grants no staff permissions: an operator must provision the exact signed subject/email in `public.staff_users` with explicit `recovery` and/or `moderation` roles. Require strong MFA in the Access policy; deployment and verification of that policy are launch prerequisites. An empty configuration fails closed. Do not create a development bypass in production.

The recovery console is `/staff`; the API is `/api/staff/recovery`. Public reports and verified safe-contact sessions are deliberately separate from ordinary member sessions. Reviewers must document corroborating established-method/security-history evidence; a supplied email, public facts or friend endorsements are insufficient. Hold and ownership restoration are serialized with auth transactions. Two different currently authorized reviewers must approve restoration. Completion revokes all old device keys and login/MFA credentials; old encrypted content still requires the member's encryption recovery secret. A denied claimant may appeal; denial does not automatically release a corroborated hold.

Case channels expire after24hours. `/api/account-recovery/resume` sends a fresh one-use contact link only to the case's verified safe email. It does not create a login session. Recovery evidence and historical login addresses expire after90days; cleanup runs with the job consumer. Define staffing, escalation and contact details before admitting real members.

Recovery preserves the member's moderation state from before the security hold. A restricted or suspended member remains restricted or suspended after ownership is restored; only a separate authorized moderation review can lift that restriction. Repeated holds cannot overwrite the saved state. Legacy holds without a trustworthy prior state return to suspended status, and recovery cannot resurrect deleting/deleted accounts. Staff queues support state filters and stable cursor pagination, including cases with equal creation timestamps.

Ordinary suspended/restricted members retain their own data export/deletion and appeals. Suspected-takeover holds block both export and deletion. Both clients restore existing keys locally for restricted/suspended accounts without enrolling a device or opening social publishing. Historical revoked keys can decrypt old content but cannot sign new evidence; an existing nonrevoked key is preferred when available. Reports without encrypted evidence remain available to restricted members. Native locked-account controls also permit owned-group resolution, deletion and appeals without requiring a content recovery secret; readable export still requires decryption keys.

Authenticator MFA uses the maintained BetterAuth TOTP/backup-code implementation. New login passwords are checked against the Have I Been Pwned password corpus using its padded hash-prefix API; plaintext passwords and full hashes are not transmitted. A provider error fails the password change safely. This adds an external availability dependency. Password reset/change and email change revoke old sessions; changing a verified email requires approval at the old address and verification of the new one.
