# Recovery when monitor history is temporarily unreadable

Normal monitor releases still require a fresh successful baseline read and retain the 30-minute continuity bound. An explicit, hash-pinned `monitor.incidentRecovery` evidence file now supports the narrower case where the current monitor returns its exact HTTP503/unknown response without history.

The incident file identifies the baseline version/source and candidate source, pins supporting evidence, and records the observed failure with its original timestamp. The historical baseline is independently pinned with its original observation timestamp and must have been a valid fresh response when captured. Recovery does not relabel either artifact as healthy current evidence.

At authorization, historical evidence must be at most six hours old, the incident observation at most30 minutes old, neither may be future-dated, and no historical minute may have rolled out of the retention window. A bounded fresh GET must either show the exact monitor-unavailable response (retained as `monitor-unavailable-baseline`) or pass recovered-history verification. Other HTTP failures, malformed responses and timeouts do not authorize activation through this exception.

After activation and before canonical finalization, the monitor must return a fresh valid200 with unchanged history origin, expected count progression, no lost passed/failed observations, and no metrics regression. The same rules apply to verifying a rollback; the pre-activation exception cannot declare either candidate or rollback healthy. Existing CI, source/artifact, schema, storage compatibility, staging acceptance, application journey, inventory, lease and one-shot transport checks remain enforced. No state reset or scheduled-tick replay is introduced.

Validation: 131 tests across monitor state/verifier and activation command suites passed; release-controller TypeScript compilation passed. Tests reject stale/future/tampered/wrong-source evidence, unsupported errors, missing history and metrics regressions. Composed tests use real journals/leases and mocked provider/database/CI/network boundaries: a lost activation reply is reconciled with exactly one deploy call, and lost candidate history retains unresolved state without replaying deployment or login. These are local controller tests, not production recovery evidence.

Production rollout must use the observed activation entry point to retain application/session checks before, during and after activation. The runtime mitigation already passed hosted staging continuity with14 samples and no failures. Production monitor repair and subsequent observation remain outstanding; no claim is made that retrying reads resolves the underlying Durable Object internal errors or that monthly99.99% has been achieved.
