# Bounded natural-observation window for monitor recovery

The first production recovery evaluated its candidate before a full cron interval had elapsed. Local persisted-state testing showed that code replacement preserves the old checked-at timestamp until a scheduled observation updates it. This establishes a timing requirement to test; it does not diagnose production's Durable Object internal errors.

For explicit, reviewed monitor incident recovery only, candidate verification now waits for a natural observation before starting the authenticated journey. It repeats fixed-origin public status GETs at two-second intervals within one durable75-second window. Each read retains HTTP status and sanitized checked-at/age diagnostics. Exact503/unknown and structurally valid stale history can wait; malformed/changed history and evidence/lease failures cannot be treated as pending success. Successful readiness still requires fresh200, preserved aggregate history and metrics continuity under the existing90-second freshness rule.

The window start/deadline is persisted before reads; restarting cannot restart the polling budget. A durable ready receipt supports one fresh read after an interruption without another polling window. Expiration without readiness produces an unhealthy result, allowing the existing independently authorized rollback; cancellation or unknown verification remains unresolved. No cron/tick, upload, deploy, login or logout is repeated by the wait helper. A final in-flight read remains subject to its five-second bound and cannot be accepted after the window deadline.

The provider-neutral controller permits a fixed120-second candidate-verification budget only for an explicitly selected monitor recovery. The maintained command derives that selection from the validated incident review. Ordinary releases and rollback verification keep their45-second bound; authorization and provider-write deadlines are unchanged. The option is captured before asynchronous authorization so it cannot be changed mid-operation.

Validation:157 targeted state/verifier/composed-controller tests passed, followed by23 controller tests and typecheck after adding the immutable-budget guard. Tests include unavailable-to-fresh and stale-to-fresh observations, cancellation, fixed expiration across restart, resuming a ready window, history corruption, ordinary timeout preservation, application scope rejection, and a composed observed activation with delayed freshness, one deployment and one authenticated journey. Provider, CI, database and network boundaries in composed tests are mocked; these are not production recovery results.

Production remains on its original monitor with503/unknown. The previous failed operation was archived as failure and cannot replay. The verified inactive candidate can be reused by a new activation plan with fresh inventory/incident evidence and exact current-tooling CI; upload-time tooling is independently pinned by its archived proof. No second production activation has started at this writing.
