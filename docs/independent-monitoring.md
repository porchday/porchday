# Independent service monitoring

`apps/monitor` is a separate Cloudflare Worker. It has no PostgreSQL, Hyperdrive, application R2, queue, or member-session binding. Its one-minute cron checks the selected environment's protected `/api/operations/health` endpoint. A SQLite Durable Object stores only check counters, incident timestamps, delivery retry state, and generic service/monitoring status. An optional independent Analytics Engine reader checks latency, API errors and telemetry freshness; it never receives application database or member-content access. The application never calls this Worker; a monitor, email, or state-storage failure cannot delay a member request.

The application endpoint checks cleanup heartbeat age, deletion queues, identity removal, account email backlog, and restore-journal readiness. The monitor makes a ten-second request to a fixed compiled target, does not follow redirects, caps the response at 16 KiB, and discards all protected diagnostic fields after deciding whether the response is healthy. It stores no account, post, device, email-content, or database identifier. Requests and provider response bodies are never logged.

Three consecutive failed checks open an incident. A successful outage email is followed by at most one reminder every six hours. Two consecutive healthy checks produce a recovery email, provided an outage email was delivered. Duplicate cron invocations in the same minute do not produce additional checks or messages. Delivery failures retry after five minutes with exponential backoff capped at one hour. Retry state is persisted before sending. A crash after provider acceptance but before storing success can produce a later duplicate; exactly-once delivery is not promised. A ten-second email timeout bounds the monitor's execution even if the provider stalls.

The public `/` path serves an accessible Porchday status page with a generic availability message and last checked time; `/status` returns only `status`, `last_checked_at`, and a fixed `metrics_monitoring` readiness value (`not_configured`, `checking`, `ready`, or `unavailable`). Status is `checking`, `operational`, `degraded`, or `unknown`. More than three minutes without a completed check yields `unknown`; a state-storage failure also returns generic unknown with HTTP 503. Every response is uncached and uses a restrictive CSP. The HTML has no scripts, external assets, or tracking; only fixed status/readiness text and a validated, escaped timestamp can be rendered. Confirmed latency or error incidents make service status degraded. A metrics-query or ingestion failure changes the separate readiness field; it does not assert that the member application is down. Passing availability checks alone does not establish performance-monitoring readiness. A refresh link reads the latest completed observation without triggering a new probe. There is no public check, test-email, or administrative trigger. The scheduled handler alone forwards a fixed internal request to the Durable Object.

## Latency, errors and telemetry loss

When explicitly enabled, the monitor requests the fixed public `GET /health` endpoint once per completed minute tick and reads one fixed aggregate query every five minutes. The existing protected health check continues independently every minute. Duplicate cron ticks are suppressed by the same Durable Object gate; a crash before persisting a completed tick may repeat an observation. No member identity, synthetic account, request marker, token-bearing URL, or private content is used in this path.

The query uses the environment's fixed dataset, schema and route allowlists, a 15-minute window, weighted request/error counts and `quantileExactWeighted(0.95)`. It excludes both `/health` and `/api/operations/health` from the API error denominator, and excludes OPTIONS/HEAD. Query input cannot accept an arbitrary dataset, SQL, hostname or account path. Responses are limited to 16 KiB and the fixed route count; numbers, timestamps, sampling consistency and duplicate rows are validated. Raw query responses are discarded and never stored or logged.

Each objective has independent incident/recovery state:

- **Feed latency:** estimated p95 greater than 500 ms, with at least 100 weighted GET feed requests and 20 observed sampled rows in the window.
- **API errors:** estimated 5xx rate at least 1%, with at least five weighted errors, 100 weighted API requests and 20 observed sampled rows. Expected 4xx authentication/authorization failures do not count as server errors.
- **Telemetry:** the query fails or lacks a GET `/health` observation newer than five minutes. The monitor sends a heartbeat even when no members are active, so empty data is never assumed to mean a healthy idle service. This is route-level ingestion evidence, not proof that every individual point arrived. A new reader receives a five-minute warmup allowance for an empty successful query; query failures receive no warmup exemption.

Three consecutive bad five-minute polls open an incident; two adequate healthy polls recover it. Query failures are therefore detected in roughly 10–15 minutes, while telemetry loss can take up to about 20 minutes including the five-minute ingestion allowance. The 15-minute performance windows overlap; these are sustained threshold checks rather than independent statistical trials. An insufficient sample breaks the consecutive sequence and cannot clear a performance incident. Feed-latency recovery needs enough feed traffic; an API-error incident can recover on API/auth traffic without requiring unrelated feed traffic. Weighted estimates and the minimum observed-row guard reduce misleading small samples but do not establish confidence intervals or production capacity.

Availability, telemetry, latency and error incidents share at most one email attempt per minute tick, in that priority order. Each has its own persisted five-minute-to-one-hour retry and six-hour reminder state. A failed delivery on one channel does not suppress the next eligible channel. Query and heartbeat calls run in parallel with availability checking, each bounded to six seconds; availability is bounded to ten seconds and the single email attempt to ten seconds. This leaves margin below the Durable Object concurrency gate's 30-second limit. A query/heartbeat failure does not prevent availability checks or application requests.

Metrics readiness becomes unavailable after seven minutes without a completed metrics poll, even if minute availability checks still succeed. Disabling metrics resets their private alert state and makes readiness `not_configured`; it never silently reports ready. Admission requires this consumer to be enabled and its actual remote alert/recovery delivery verified.

## Configuration

Run `python3 scripts/configure-monitor.py staging` or `production` to render the separate deployment configuration with metrics disabled. Add `--enable-metrics` after obtaining the dedicated read capability to enable aggregate monitoring. This does not deploy it. Production uses `status.porchday.com`; staging uses `staging-status.porchday.com`. Each deployment owns its Durable Object namespace and alert state. The generated configuration enables the minute cron, a 1,000 ms CPU limit, native Cloudflare Email Service, and sanitized logs without invocation logs or traces. The local base configuration has no cron or remote email binding.

Install these values through the private secret workflow:

- `OPERATIONS_HEALTH_TOKEN`: the same environment-specific token installed on the application. This authenticates only the aggregate health endpoint, never a member or staff session.
- `MONITOR_RECIPIENT`: the operator's chosen monitored email address. Keep this out of committed configuration and logs.
- `CLOUDFLARE_ANALYTICS_READ_TOKEN`: when metrics are enabled, a dedicated **Account Analytics / Read** API token restricted to this Cloudflare account. Do not use the deployment token or grant write/management permissions. The runtime has no fallback to `CLOUDFLARE_API_TOKEN` or another credential. Cloudflare account scope can read other account datasets; it is not claimed to be dataset-restricted.
- `EMAIL_FROM`: a verified sender on the configured Cloudflare Email Service domain. The generated config currently uses `Porchday <accounts@porchday.com>` with that sender allowlisted.

Deploy only after the application hostname exists, its operations token is installed, the email sender is enabled, and an operator recipient is configured. Keep staging and production tokens distinct. Review the generated routes before deployment; do not overwrite an existing unrelated status site. Check the public status, then perform an authorized controlled staging incident to verify actual email delivery and recovery before treating alerting as operational. Unit tests use an injected email service and do not send mail.

`python3 scripts/with-secrets.py python3 scripts/upload-monitor-secrets.py staging --check` validates private configuration without uploading. Omit `--check` after the target monitor is deployed to upload through stdin. Use `production` for the other environment. The recipient defaults to the configured Cloudflare account owner, matching the existing budget alert; set `PORCHDAY_OPERATIONS_EMAIL` in the private secrets file to choose another monitored address. Name a backup responder before real-member admission. For enabled metrics, set `PORCHDAY_STAGING_ANALYTICS_READ_TOKEN` / `PORCHDAY_PRODUCTION_ANALYTICS_READ_TOKEN`, or a shared dedicated `CLOUDFLARE_ANALYTICS_READ_TOKEN`, in the private secrets file. The uploader rejects a missing token or one equal to the supplied deployment token. Its `--check` validates format/configuration/distinctness, not the token’s actual permissions: verify those during token creation and confirm the scoped SQL read succeeds before deployment. No recipient or capability is printed. A disabled check succeeds for availability setup but explicitly says metrics are not ready for pilot admission.

## Operations and limitations

A 30-day month produces approximately 43,200 protected health checks per environment. Enabled metrics add 43,200 public heartbeat requests/points and 8,640 SQL reads per environment, plus two small durable state records and low alert volume. Both environments together make approximately 17,280 monthly metrics queries; these are separate from operator queries and public status traffic. Public status visits add reads. Track actual Workers, Durable Objects, and email usage against the setup/operating budget; no paid third-party monitor is required for this path.

This monitor is independent of the application and database, but shares Cloudflare's platform and email service. A broad Cloudflare outage can affect both checking and alert delivery. Configure a separately operated uptime check or Datadog check of the public status endpoint when that account is available, including detection of stale `last_checked_at`. The public timestamp helps an outside checker detect a stopped cron; the Worker cannot email through a complete outage of its own platform.

Troubleshooting logs contain only `monitor/check_failed` or `monitor/alert_retry` and the environment. Inspect private aggregate application health to diagnose the underlying problem. Do not temporarily add response bodies, tokens, URLs containing secrets, recipient addresses, or raw exception messages to logs. Storage failures deliberately stop untracked mail attempts. Email delivery configuration needs separate operational verification; a green application status does not itself prove an operator email can be received.

`apps/monitor/test/monitor.test.ts` covers fixed target and redirect policy, bounded input, timeout/cancellation, thresholds, concurrent duplicate ticks, reminders, retries, redaction, storage isolation, no public trigger, and stale public state. Additional metrics/configuration tests cover idle-heartbeat freshness, separate threshold/recovery evidence, weighted/observed sample guards, bounded queries and timeouts, missing/dedicated credentials, concurrent incident retries, continued health checking during query failure, and private state/output redaction. The Worker also passes Wrangler's packaging dry run; this is not evidence of remote deployment or successful real alert delivery.

Implementation references: [Cloudflare cron triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/), [Durable Object state and concurrency](https://developers.cloudflare.com/durable-objects/api/state/), and [Email Sending Workers API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/).

The new aggregate consumer has been verified locally with injected query/email services. The deployed monitor, dedicated token scope, hosted freshness and controlled remote incident/recovery delivery have not yet been verified by this implementation work. On 2026-10-25, the primary agent executed the exact consumer SQL against the existing isolated verification dataset (only the dataset name changed): Cloudflare accepted it and returned no current-window rows, as expected. A second query with a two-hour historical window returned three feed requests/observed rows, zero errors and p95 12 ms; the parser accepted the real timestamp/numeric response shape using a historical reference time. This did not emit new points, deploy anything, satisfy the performance sample floor, or verify current freshness. Existing isolated exporter/query-helper evidence does not establish that these alerts are live.
