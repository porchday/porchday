# Native comments and reactions interoperability

This is a bounded, opt-in staging acceptance check. Preparation is implemented; a hosted run has not yet been performed. It supplements the earlier successful [post/photo interoperability check](hosted-native-verification.md). It does not substitute for UI accessibility checks or an independent cryptography review.

The fixture uses only surviving synthetic member A. B's recovery case and deleted member C are untouched. The JavaScript side uses the maintained OpenPGP.js package; the native XCTest uses the shipped `AppModel`, `API`, `CryptoVault`, `CommentDeadline`, Keychain and GopenPGP paths. No credentials, private keys, fixture values, raw test logs, screenshots or xcresult bundles are published.

## Contract and boundaries

`scripts/hosted-social-interop.ts prepare --run --attempt=<8 lowercase hex>` performs normal sign-in, snapshots A's profile, full device records and encrypted recovery backup, then exclusively writes an immutable private intent before the first content mutation. It creates exactly one `only_me` post, one shorter comment and one shorter reply, all expiring within two hours. It adds the existing catalog reactions `like` and `love` to both the post and the comment. Private artifacts live under the ignored, owner-only `artifacts/private/hosted-smoke/native-social-<attempt>-*` paths. A reused attempt fails before content publication. Failed preparation attempts to delete only its preallocated parent and preserves a failure receipt; it never replays uncertain publication. A timed-out or otherwise unconfirmed publication keeps cleanup explicitly unconfirmed even if an immediate read reports the parent missing, because a late commit remains possible.

The version 2 fixture selects `HostedSocialInteropTests/testHostedCommentsAndReactions` in the existing manual hosted workflow. Release builds retain the production origin; the staging override requires both a Debug build and the explicit test flag. The fixture expires within two hours and must have more than 45 minutes remaining at test start. The operator waits for root review before preparation and dispatch, places only the synthetic fixture in the ephemeral `PORCHDAY_IOS_HOSTED_FIXTURE_B64` repository secret through stdin, and deletes that secret after the workflow terminates or is cancelled, verifying its absence.

Native enrollment uses the ordinary recovery proof and atomic protected-backup update. The test captures the device ID returned by successful enrollment. It decrypts the JavaScript post/comment/reply and both reactions, then creates one comment inheriting the exact post deadline and a reply with an explicitly shorter 20-minute absolute deadline. It adds `laugh` and `celebrate` twice on each target, verifies that repeated identical tags remain one reaction, removes `laugh`, and verifies that each target retains exactly three reactions. Finally it revokes only the fresh, captured native device and signs out. A partial enrollment whose ID was not captured is reported as unconfirmed; the test never guesses an ID from a roster difference to revoke it. Cleanup failures are reported separately without masking the original failing phase.

`check --run --attempt=<attempt>` independently decrypts every fixture object using A's original JavaScript private key. It verifies the signed author/object/parent/audience/deadline context, exact synthetic payloads, inherited deadline, shorter deadline, and canonical per-person reaction tags. It reads the revoked author's historical public key through the normal API, requires a unique newly revoked device, and checks that all preexisting device records, profile ciphertext, recovery key and prior encrypted backup entries are unchanged. The new revoked device and its encrypted backup entry intentionally remain as historical records. The active device set returns to its baseline; the total roster is not claimed to be byte-for-byte unchanged.

`cleanup --run --attempt=<attempt>` deletes only the immutable parent ID, verifies parent 404 and child DELETE 404, then rechecks the baseline using the native ID recorded by successful independent verification. It does not revoke a device. If a native run fails before successful verification, cleanup can still remove the fixture parent; any extra device is explicitly left unconfirmed for operator review. Reactions are no longer readable through the missing parent; physical foreign-key cascades are covered by SQL tests rather than an invented read endpoint. This fixture has no photos or R2 objects. All three phases sign out and replay their saved cookie against the real member API to confirm session revocation.

Root must keep A exclusive during prepare, hosted execution, independent check and cleanup, and avoid staging deployment during the run. Each phase writes a private timestamped result and emits fixed status codes only. The independent content-verification record is saved before logout so cleanup can use its observed author ID even if logout fails. Only the phase result with `complete: true`, written after logout cleanup, establishes success; existence of the fixture or verification file alone is insufficient. A failed attempt remains evidence and is not silently retried.

## Local checks and limits

Pure guard tests cover explicit invocation, A-only selection, unchanged prior keys/profile, exact captured-device cleanup, object/context binding, and fixed-code refusal without private-state access. The hosted runner tests retain the original version 1 post/photo contract while requiring exactly the selected version 2 test to pass, with zero skipped tests. Local Swift parsing can check syntax; actual native compilation and execution still require the macOS CI workflow. No hosted success is claimed until its one XCTest and the independent JavaScript verification both pass.
