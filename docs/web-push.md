# Web Push operations

Porchday uses `web-push` 3.6.7 to generate RFC 8291 `aes128gcm` request bytes and VAPID authorization, then sends those bytes with the Workers `fetch` API. It does not use the library's Node HTTPS delivery transport. Local `workerd` verification covered P-256 subscription validation, ECDH encryption, and VAPID request generation under `nodejs_compat` on compatibility date `2026-10-24`.

Set `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, and `VAPID_SUBJECT` for each environment. The subject must identify the operator with a monitored `mailto:` contact or an HTTPS contact URL. Generate the key pair once using `web-push.generateVAPIDKeys()` and store the private key through the deployment secret workflow; do not print or commit it. The public key is intentionally returned to authenticated browsers by `GET /api/v1/push/config`. Absent any required setting, that endpoint reports `enabled:false` and the queue processor makes no push requests. Rotating the signing key requires members to subscribe again with the new public key.

Members explicitly enable push in Settings before the browser asks permission. `POST /api/v1/push/subscriptions` validates a browser's P-256 public key, authentication secret, and HTTPS endpoint, and opts the account into push. Only production FCM, Mozilla, Apple Web Push, and Windows notification service hosts are allowed; redirects are forbidden. Up to ten subscriptions are allowed per member. Subscription endpoints are capabilities and must never be logged, exported in telemetry, or exposed to other members.

Subscriptions are bound to the authenticated session in PostgreSQL. Deleting that session, revoking all sessions, deleting the member, entering a security hold or suspension, or disabling push removes subscriptions and their queued deliveries. `DELETE /api/v1/push/subscriptions/:id` removes an owned browser subscription. `DELETE /api/v1/push/subscriptions` disables push and removes all of the member's subscriptions. The browser also unsubscribes locally during opt-out/logout. Restored accounts explicitly opt in again.

An insertion into `app.notifications` queues one durable `app.push_outbox` row for each opted-in subscription. `processWebPush(env)` claims at most twenty deliveries per invocation, with four network requests in flight at a time, two-minute leases, and an eight-second timeout. Immediately before sending, PostgreSQL rechecks the session, member status, preferences, unread state, blocks, mutes, and current content/group access. Deleted notification targets cascade away; expired content is rejected independently of cleanup timing.

The encrypted push payload is always exactly the same public preview: title `Porchday`, body `You have a new update`, and destination `/app/notifications`. It contains no member, notification, post, comment, group, or device identifier and no social content. The browser service worker also fixes the displayed preview locally. The push provider receives delivery metadata and encrypted generic payload bytes. Deliveries use a sixty-second TTL and a constant topic so crash retries replace the same generic preview; exactly-once network delivery is not promised.

HTTP 404/410 removes the invalid subscription. HTTP 429, 5xx, 401/403, and transport errors retry with bounded exponential backoff and `Retry-After`, up to eight attempts or twenty-four hours. Other HTTP errors finish the job as failed. No provider response bodies are read or logged. Expired/failed/sent outbox metadata is retained for seven days, then pruned; endpoint records are separately removed on session expiration. Monitor aggregate retries and oldest pending work through the existing jobs monitoring; never include endpoints or keys in alerts.

The test suite `apps/api/test/push.test.ts` validates actual encrypted request bytes and uses injected fetch responses instead of contacting live push services. Set `PUSH_TEST_DATABASE_URL` to a disposable PostgreSQL database whose name contains `push_test` to run database authorization, session cascade, opt-out/status/access checks, 429/410 behavior, lease reclamation, and attempt exhaustion tests. That test fixture recreates only its explicitly named disposable database schemas. The local main database has migration `025_web_push.sql` applied; deployment still needs the normal migration process.

APNs for the native app is a separate provider integration and requires the operator's Apple identity and signing setup. This implementation does not claim to deliver native APNs notifications. On compatible iOS versions, the installed Home Screen PWA can use the browser Web Push path.
