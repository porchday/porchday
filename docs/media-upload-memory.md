# Bounded encrypted photo uploads

The encrypted object limit remains exactly **22,020,096 bytes**. A reservation accepts up to 25 MiB of JSON, including its routing fields; upload bytes must match the reserved exact size. These two authenticated media routes enforce actual streamed byte counts themselves, avoiding the generic middleware's retained whole-body copy. Unknown or misleading Content-Length cannot bypass the cap. Origin and session rejection happen before their bodies are consumed.

Reservation and stored-object validation use the pinned `@streamparser/json` 0.0.26 tokenizer/parser with an isolated accumulator adapter in `apps/api/src/media-json.ts`. The upstream accumulator drops raw U+FEFF at decoder boundaries and retains excessive cons-string nodes for unpaired-surrogate escapes. The adapter preserves UTF-16 code units using bounded UTF-8 buffers and small flat string chunks, without changing the JSON grammar or global decoder. It checks the private dependency interface before use; upgrading this exact dependency requires rechecking the adapter and differential tests. One leading document BOM is accepted; misplaced BOMs, malformed UTF-8, trailing JSON, excessive depth (over 16), and excessive tokens (over 100,000) fail closed. Limits accommodate the schema's 4,000 recipient entries. Duplicate keys retain JSON.parse's final-value behavior.

Canonical envelope SHA-256 remains byte-for-byte compatible with the existing `canonicalJson` representation. The large ciphertext string is hashed in bounded, complete UTF-16 chunks through maintained native SHA-256. PostgreSQL stores only routing metadata and the canonical digest; the private object has a separate SHA-256 over its exact uploaded bytes.

Each Worker isolate grants one nonwaiting permit for large parsing/hashing work. A concurrent request receives 429 with Retry-After: 1; its body is not queued for later parsing. The network upload and subsequent stored-object read share a 120-second deadline. Expiration actively cancels the consumed stream, including a stalled R2 metadata read, and final publication checks the deadline again. This is a memory control, not a whole-service rate or capacity guarantee.

Uploaded bytes first enter the reserved private R2 key using create-only conditional storage. The row remains pending and unavailable to readers until the digest, routing, size, ownership, current write permission, and expiry checks pass. Network streaming occurs outside database transactions. Final publication locks and rechecks the reservation. Error cleanup acquires an owner-scoped row lock through migration 037, which can distinguish a ready row hidden by a later account hold from a deleted row. It checks the exact owned object ETag and never removes ready or attached bytes after an ambiguous COMMIT. Existing media tombstones prohibit key reuse.

Deletion revokes reads immediately and attempts physical deletion immediately. Its outbox entry remains unresolved until a second successful delete at least 10 minutes after the deletion, covering an already-running bounded upload that completes after the first delete and then crashes before cleanup. With a healthy minute scheduler, final confirmation ordinarily follows that 10-minute floor by one scheduling interval; outages can delay physical cleanup and are monitored. Abandoned pending reservations retain their existing 24-hour cleanup. Failed COMMIT or cleanup uncertainty leaves bytes private and relies on these durable paths, rather than guessing that a committed object may be deleted.

## Verification evidence

The real PostgreSQL HTTP suite covers signed/encrypted uploads, tampering, RLS, profile attachments, a lost COMMIT response followed by an account hold, and deletion-outbox-first ordering followed by a late writer. Focused tests compare canonical digests and JSON decoding across Unicode, BOM, duplicate/prototype keys, escapes, surrogate/chunk boundaries, malformed input, byte/depth/token bounds, reader cancellation, unauthorized requests, stream deadlines, and the memory permit.

On 2026-10-25, `scripts/probe-media-workerd.ts --run --upload --overlap` loaded the complete production Worker module (127 API routes plus fetch/scheduled/queue entrypoints), used real restricted-role PostgreSQL/Hyperdrive and native local R2, and uploaded an actual signed/encrypted OpenPGP envelope padded to the exact 22,020,096-byte limit. Sampled heap plus backing storage peaked at 74,035,849 bytes during reservation and 130,994,639 bytes during PUT. The overlapping reservations returned one 201 and one 429. These are CDP samples, which can miss transient peaks; local workerd demonstrably does not enforce the hosted 128 MiB limit. They establish functional and local memory evidence, not production capacity or a hosted memory-limit pass. Hosted verification is recorded separately by the cloud probe and must not be inferred from these numbers.

An independent adversarial accumulator check measured roughly 2 MiB retained heap for 4 MiB of repeated lone-surrogate escapes, versus roughly 37 MiB with the unadapted dependency. Differential checks against fatal UTF-8 decoding plus JSON.parse also preserved raw/escaped U+FEFF and negative zero and rejected malformed UTF-8. These focused checks do not replace the hosted exact-limit and malformed-content probes.
