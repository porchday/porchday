# Isolated hosted restore drill

This procedure tests an actual PlanetScale point-in-time restore together with the live staging R2 media snapshot and independent privacy journal. It creates temporary, private targets. It does not change either live application's bindings or quarantine the live source. A completed local dump/restore drill or synthetic Worker probe is not evidence that this hosted procedure has passed.

The operator must coordinate the fixture and source-write window before execution. Keep admissions closed. Preserve the web/native interoperability fixture until those checks are complete; use separate, clearly synthetic test records for restore assertions. The execution evidence below distinguishes completed phases from unverified recovery steps.

## Owner-requested snapshot

Migration `039_manual_media_backups.sql` adds an invoker-rights owner function. Public, auth, social and jobs roles cannot execute it. The daily `day` uniqueness constraint remains; manual inventories have `day = NULL`, so they cannot overwrite the day's scheduled run. A UUID/time retry returns its existing inventory, never captures a new one. Both types expire exactly seven days after their paired timestamp.

After applying the migration and deploying the queue consumer, an authorized operator can run:

```sh
python3 scripts/with-secrets.py npx tsx scripts/start-media-backup.ts staging --run
```

The command accepts only the environment-specific migration credential and checks its PlanetScale branch suffix against `infra/resources.json`. It requires an active, zero-pending journal matching the source database. It obtains the paired UTC time in a separate SQL statement before the frozen inventory scan, persists an operator ticket under ignored `artifacts/private/restore-ops/manual-media-backups/` (directory mode 0700, file mode 0600), creates the inventory, verifies the same zero-pending source control and database sequence after capture, and sends the ordinary `media_backup` queue message. It neither uploads owner credentials to the Worker nor introduces a public backup route.

If SQL/queue confirmation is ambiguous, resume using the existing ticket's UUID rather than create another run:

```sh
python3 scripts/with-secrets.py npx tsx scripts/start-media-backup.ts staging --run --resume=RUN_UUID
```

A retry whose inventory was never committed and whose paired timestamp is now more than a minute old fails closed. A changed source checkpoint before capture confirmation also fails closed; do not reuse an unconfirmed inventory against a different source cut. Inspect the run before creating a fresh ticket. A queued response is not completion: require a complete, unexpired immutable manifest from the ordinary native-R2 copier, verify its entire chain and raw hashes, and record its exact `run.restore_at`. The copier can initialize missing R2 state from an existing generation-checked frozen SQL inventory; it cannot replace existing state or completed snapshots. Duplicate queue messages retain the normal CAS lease/cursor behavior.

## Fixture and timing sequence

1. Run `npx tsx scripts/hosted-restore-fixtures.ts prepare --run --attempt=ATTEMPT_NONCE` only in the coordinated window. It reuses the protected synthetic staging account state, leaves the native interoperability fixture unchanged, and uses the actual invited-member HTTP API to create a surviving encrypted post/photo and a second post/photo to delete. Add a timed thread with a deadline comfortably beyond the snapshot and test window. Retain the private client keys locally for final decryption. Keep client state in the protected ignored operator artifact directory. Use a fresh eight-hex attempt nonce; its fixture ticket is exclusive and cannot replace an earlier attempt. The legacy default ticket remains readable for the original attempt.
2. Request the manual snapshot and wait for the complete manifest. Verify both photo objects are included; preserve the earlier bootstrap snapshot. Record its exact paired timestamp and current journal sequence. The database timestamp precedes inventory capture, so the later provider restore must use that exact timestamp rather than the time the copy finished.
3. Run `python3 scripts/with-secrets.py npx tsx scripts/hosted-restore-fixtures.ts after-snapshot --run --snapshot=RUN_UUID --attempt=ATTEMPT_NONCE`. It verifies the complete snapshot and inclusion of both photos before using the actual member API to delete the designated post/photo and shorten the timed thread, waiting for the API's independent journal acknowledgment. Include a child comment to check inherited deletion. Do not directly modify SQL fixtures to simulate member behavior.
4. Coordinate a brief source privacy-write pause while taking the latest stable journal cut. Ordinary source reads continue. Scheduled cleanup may advance the sequence, in which case the copy refuses and the operator chooses a new target/cut. This is a finite test cut, not a claim that future source deletions are automatically mirrored to the isolated target.
5. Wait until PlanetScale's available WAL restore window includes the paired time. Its current documentation describes recovery through approximately five minutes before the present; verify actual availability and the preceding base backup. Daily snapshot retention alone does not prove that an exact timestamp is restorable. [PlanetScale PITR](https://planetscale.com/docs/postgres/backups/point-in-time-recovery)

## Isolated targets and journal cut

Use a fresh eight-hex nonce. Create a temporary `porchday-restore-NONCE` PlanetScale branch in the staging database, economical PS-5 ARM, zero replicas, PostgreSQL 17 inherited from the source, us-west, and the minimum storage accepted for the selected base backup (the first real attempt required 20 GiB). Use `pscale branch create` with `--from main --restore-point PAIRED_TIMESTAMP --cluster-size PS_5_AWS_ARM --replicas 0 --region us-west --min-storage 21474836480 --max-storage 21474836480`. Confirm the installed CLI's argument order and provider response before running; preserve the actual requested/restored time privately. Poll readiness without blocking the operator for long intervals. Do not use the source branch's credential against the target or reset the source's role passwords. [PlanetScale create-branch API](https://planetscale.com/docs/api/reference/create_branch)

Create distinct private R2 buckets `porchday-restore-NONCE-journal` and `porchday-restore-NONCE-media`, with managed public domains disabled and no custom domains. No public app, Hyperdrive, scheduler, email job or push job should target them. The existing staging media-backup bucket is a read-only snapshot source. Record a crash-cleanup deadline and resource IDs privately; delete temporary resources at the end rather than extend backup retention.

Set `RESTORE_DRILL_JOURNAL_BUCKET` only in the private operator environment, then run:

```sh
python3 scripts/with-secrets.py npx tsx scripts/clone-journal-for-drill.ts staging --run
```

The source adapter only reads. The target uses the existing temporary authenticated native-R2 operator bridge and verified atomic conditional writes. The copier verifies every immutable batch through the production journal verifier, refuses any pending operation or database tail beyond the independent checkpoint, and checks that source generation/sequence/head/control and database sequence remain unchanged before and after copying. It publishes target control only after verifying the complete chain, preserving generation/head/sequence but forcing quarantine. It checks again after publication; any uncertainty leaves an unused quarantined target. The short-lived operator Worker and custom domain are torn down and their absence verified. No source receipt, intent, control or session is mutated.

An initialized target cannot be silently replaced. If a copy fails, leave it unused and remove it as an isolated artifact after recording the failure. A fresh successful cut is needed; do not release an uncertain target. This does not replace the source quarantine required for a real disaster restore, where all writers must be stopped and unresolved intents reconciled.

## Restore checks and release

1. Capture the provider's exact PITR result and elapsed provisioning time. Reset credentials only for the restored target's managed owner/runtime roles; retain restored object ownership and grants. Store new credentials with mode 0600, never in arguments/output. Before replay, verify that the snapshot contains the soon-to-be-deleted records and pre-restore sessions; this proves the later disappearance comes from reconciliation.
2. Point a private operator process at the isolated target DB, journal and media. Do not edit live `infra/resources.json` bindings. Optionally copy the selected snapshot's to-be-deleted media into the target before replay using the same native operator copy path, proving that replay removes physical stale bytes as well as rows. No source media object is deleted.
3. Run `restore-safety.ts replay` against the target with the cloned latest journal. Assert deleted content/children are absent, shortened expired content cannot read, all restored sessions and integration capabilities are invalidated, and relevant credential-change holds survive. Verify runtime auth/social/jobs privileges remain separated with no owner role memberships.
4. Run `restore-safety.ts restore-media` using the exact manifest timestamp. It restores only still-required bytes, checks complete inventory coverage and both database digests, and never reintroduces journal-deleted media. Test a missing required target object causes release refusal, then restore that object through the verified path.
5. Review the target sequence, run `release`, and check the target's social role: the owner can read/decrypt the surviving post/photo using locally retained keys; an unrelated member cannot. Deleted/expired targets remain absent. The target stays unbound to public app traffic even after release.
6. Record aggregate assertion results and phase durations. Delete the temporary branch and private target buckets (including any copied ciphertext), then independently verify they and the operator Worker/domain are absent. Preserve only sanitized evidence and the private operator tickets required for audit. Report temporary incurred costs separately from live recurring capacity.

The evidence should distinguish provider PITR success, journal replay, media integrity, cryptographic decryption, role/session isolation, release refusal, and cleanup. A failure at any phase is a failed hosted drill until resolved; no snapshot or source fixture should be silently rewritten to make it pass.


## Restore administrator command-path inventory

Migration `040_restore_operator.sql` adds explicit rights for the provider's existing `postgres` administrator. It does not change object ownership, function bodies, SECURITY DEFINER settings, RLS policies or runtime role privileges. The provider administrator already has `pg_read_all_data`, `pg_write_all_data` and `BYPASSRLS`; these broad administrator capabilities must never be bound to a running app Worker. The additional grant of `USAGE, CREATE ON SCHEMA app` satisfies the existing `session_user` restore gate. No runtime login receives that grant.

| Command/path | Explicit function privileges | Other existing administrator operations |
| --- | --- | --- |
| `initialize`, `checkpoint-original` | `app.safety_status()`, `app.safety_page(bigint,integer)` | Read journal state/pages; `checkpoint-original` still requires an explicit unrestored-primary attestation |
| `verify`, `quarantine`, `reconcile-receipts` | None | Native R2 journal operations only |
| `replay` | `app.safety_status()`, `app.replay_safety_batch(jsonb)`, `app.set_security_hold(uuid)`, `app.expire_batch(integer)` | Quarantine/update safety state, replay decisions, revoke restored identity/session/integration/push/email capabilities, complete deletion outboxes and refresh the directory epoch |
| `restore-media` | `app.safety_status()`, `app.media_deadline(uuid)` | Read surviving asset metadata; create/drop a connection-local temporary proof table; verify/copy native R2 bytes |
| `release` | `app.safety_status()`, `app.comment_deadline(uuid)`, `app.media_deadline(uuid)` | Read remaining cleanup blockers, independently hash every required object, update the quarantine flag and conditionally publish active journal control |
| Replacement auth/social/jobs credentials | ADMIN on the matching existing base role | Create separate provider-managed logins with no initial inherited roles; grant exactly one matching base group to each login |

The three base-role grants to `postgres` use `ADMIN TRUE, INHERIT FALSE, SET FALSE`; recovery administration does not make those runtime groups automatically inherited or settable. Replacement runtime logins remain `NOSUPERUSER NOCREATEROLE NOBYPASSRLS`, with no `app` CREATE, no restore replay permission, no owner/operator membership and exactly one inherited/settable base group. The manual snapshot function remains owner-only and is not granted to the recovery administrator. Future restore-command changes must update this explicit call inventory and its real-PostgreSQL permission test before deployment.

The local regression uses a non-superuser, non-owner operator with PlanetScale's existing read/write/bypass administrator capabilities. Its initial owner-function call is denied. It then applies the exact grant statements with only the local grantee name substituted (local `postgres` is a superuser), closes the original owner connection and exercises the production replay, missing-media release refusal, verified media restore and release code. It separately checks replacement-login isolation, unchanged function ownership/security settings and a credential-hold followed by account deletion. Replay retains holds only for accounts that still exist; a later deletion neither resurrects an account nor prevents recovery of surviving accounts. This verifies the grant design locally; it does not replace the new hosted PITR test required after applying the migration.

## First hosted attempt: 2026-10-25 (incomplete)

Attempt `53e914fb` used the actual staged-member API to create three posts, two encrypted photos and a child comment. The complete immutable R2 snapshot `46f5a436-faaa-4ab5-9ab3-c3252555a4ee` was paired with **2026-10-25 16:59:46.296 UTC**, at journal sequence 39. The designated post/photo deletion and shortened parent timeout were subsequently acknowledged by the live API. A stable independent journal cut through sequence 48 (17 immutable batches, 48 events) was copied into a separate quarantined target; the source control/head/sequence stayed unchanged through that copy. The live source was never quarantined or rebound.

PlanetScale created `porchday-restore-53e914fb` at 17:07:59.009 UTC, using PS-5 ARM, zero replicas and 20 GiB. The 10 GiB request was rejected because the selected base backup required at least 20 GiB. Direct inspection of the restored PostgreSQL 17.11 branch confirmed all 40 migrations through 039, all three fixture posts, both photo rows, the child comment, the known pre-snapshot session and journal sequence 39. Its last replayed transaction timestamp was 16:59:17.231 UTC; that is the last transaction before the requested PITR time, not a replacement requested timestamp. All 43 app RLS-enabled tables and original SQL role memberships/SECURITY DEFINER owners were retained.

The restore stopped before journal replay: the provider's preserved-username managed owner record returned an internal error when its credential was reset. The original runtime SQL roles survived but were absent from the target's managed-role listing. Resetting only the isolated default `postgres` credential succeeded; it could inspect restored rows through its existing provider administrator privileges, but it lacked EXECUTE on the owner-only restore functions and lacked ADMIN on the original owner role. Rollback-only privilege probes confirmed it could not grant or alter that owner. Source credentials, ownership and RLS were not changed. `pgcrypto` is not used by the schema and was not a cause of this failure.

Migration 040 addresses the missing restore-administrator privileges without depending on the managed owner credential. The fresh paired snapshot, fixture ticket and PITR attempt below verify it; the first snapshot and failure evidence remain unchanged. The first branch and both private target buckets were deleted and independently confirmed absent at **17:26:41.526 UTC**; 18 cloned journal objects were removed. No target replay, media release or end-to-end hosted recovery success is claimed for this attempt.

The temporary branch existed for approximately 18 minutes 43 seconds. Its nominal rate was $5/month compute plus approximately $1.25/month for storage above the included 10 GiB, prorated while allocated; that interval estimates below $0.01 before R2 operations. This is a rate-based estimate, not a posted invoice or a claim that provider billing has settled. [PlanetScale pricing](https://planetscale.com/docs/postgres/pricing)


## Second hosted attempt: verified and cleaned up

Attempt `efb66421` passed using a new fixture ticket and snapshot, then removed all isolated resources. The machine-readable [sanitized evidence](evidence/hosted-restore-2026-10-25.json) records the successful checks and the earlier failures separately. No secret, account identifier, decrypted content or member media path is included in that file.

- **Paired source:** immutable snapshot `0c317179-7912-40f7-b048-60567b4a5bae`, paired **2026-10-25 17:34:22.769 UTC**, completed at 17:34:34.180, with five encrypted objects / 18,929 bytes and base sequence 56. Own post/photo deletion and a shorter parent timeout were acknowledged after the snapshot. Scheduled cleanup removed the expired parent and child before the stable cut.
- **Independent cut:** sequence 65, 25 verified immutable batches / 65 events, no pending operation. The live source generation, head, control and database sequence stayed unchanged during copying. The target began quarantined and never received a public app or Hyperdrive binding.
- **Provider PITR:** temporary PS-5 ARM / zero replicas / 20 GiB branch created at 17:40:06.571, observed ready by 17:43:02.649. PostgreSQL 17.11 restored all 41 migrations through 040, original schema/function ownership, all three fixture posts, both photo rows, child comment and known session. Sequence 56 and last replayed transaction 17:34:20.624 matched the requested pre-inventory point. The restored default `postgres` credential could execute the reviewed restore path and attach three fresh, separately restricted runtime logins without the original managed owner credential.
- **Reconciliation:** the production replay code applied nine later events, advancing 56 → 65. Deleted/expired posts, the child comment and deleted photo metadata were absent; a deliberately pre-seeded stale target photo was physically removed. All 12 restored sessions and verification tokens were removed, and all three credential epochs refreshed. Auth/social/jobs privileges remained separate. There were no restored integration grants, so this attempt does not independently demonstrate revocation of a previously live integration token.
- **Media and release:** release first refused missing required media. The normal copier restored four surviving objects and discarded the deleted fifth object. All four remaining objects (15,564 bytes) matched database hashes and sizes. The final successful production release gate independently checked them again. The member decrypted the surviving post and JPEG using the original retained client key, an unrelated member could not read it, and deleted/expired content stayed absent.

The first final integrity-gate call returned `OPERATOR_MEDIA_VERIFICATION_FAILED` after copying, so the target remained quarantined. Independent REST reads found every required byte/hash correct. A diagnostic attempt to recreate a temporary endpoint encountered `OPERATOR_DNS_NOT_READY`; teardown was verified. On a new hostname all four native verification requests returned 200. The ordinary production release code then passed on another fresh endpoint, completing at **17:48:09.607 UTC**. The original error's cause was not established; it is not presented as data corruption, and the failure record was retained rather than overwritten. No gate was disabled and no bytes were replaced to obtain a pass.

Measured active phases were snapshot verification/stale-object seeding **2.886 s**, journal replay **4.237 s**, surviving-media copy **7.771 s**, and successful release **3.269 s**. The full execution included provider provisioning and the diagnostic/retry interval; these phase measurements are not an RTO guarantee. All temporary operator Workers and custom domains passed their bridge teardown checks. The second branch and both private buckets were independently confirmed absent at **17:49:42.018 UTC**, including all 26 cloned journal objects and surviving copied media. Live bindings remained unchanged. Its approximately 9 minutes 35 seconds of allocated capacity estimates below $0.01 at the quoted compute/storage rates, excluding R2 requests and pending provider billing.

This establishes the tested hosted recovery procedure for a coordinated synthetic staging cut. A real incident still requires stopping source writers, reconciling uncertain intents, restoring the appropriate current journal and rechecking staff identity and runtime credentials before admitting traffic.
