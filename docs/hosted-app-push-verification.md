# Application Web Push verification procedure

The opt-in `scripts/hosted-app-push.ts` check exercises only synthetic staging A/B. It requires an explicit fresh eight-hex-digit attempt: `node --import tsx scripts/hosted-app-push.ts --run --attempt=<attempt>`. Run only after the operator confirms no concurrent staging/fixture activity and an independent guard review. Do not rerun a failed attempt blindly.

The authorized exception is narrowly defined: both accounts must still be active, in-app notifications enabled, push disabled, no friendship or pending request, and only A blocking B. A must have no existing push subscriptions. The check signs in normally, uses a **new owner-only installed-Chrome profile**, and never unlocks or enrolls encryption keys. The public staging page loads the unmodified deployed service worker. A real `PushManager` subscription uses the deployed public VAPID key and is registered through the ordinary authenticated application API. Permission is granted only in this temporary profile. The user’s browser and OS settings are untouched.

After registration, the script temporarily removes only A→B’s block and sends exactly one ordinary B→A friend request with a preallocated UUID. It never accepts the request. It checks the corresponding real unread notification, waits at most three minutes for normal cron and actual provider delivery, and observes the hosted service worker’s generic notification through `getNotifications()`. It does not send directly to the provider, invoke cron, inject events, insert SQL notifications or call `showNotification` itself. The separately recorded transport-only check remains narrower evidence until this application check passes.

Before each mutation, an exclusive mode-0600 intent receipt records only fixed operation labels and captured synthetic IDs. `artifacts/private/hosted-smoke/app-push-<attempt>.captured.json` contains `aId`, `bId`, `requestId`, `subscriptionId` and only a hash of the endpoint. It is written before the friend request. A later numbered `notification-captured` receipt contains `notificationId`. No subscription endpoint capability, provider key, session token, password, private content or encryption key is written to receipts or logs. Existing fixture credentials are read privately; ordinary session cookies remain in memory or the disposable browser profile.

When the fixed `awaiting-independent-outbox-read` stage appears, the operator has sixty seconds to observe the single outbox row read-only. Join `app.push_outbox q` to `app.notifications n` on `n.id=q.notification_id`, filtering exact captured `q.subscription_id`, `n.recipient=aId`, `n.actor=bId`, `n.kind='connection_request'`, and `n.dedupe_key='request:'||requestId`. Do not select endpoint/keys or use SQL to alter delivery. The operator writes an exclusive owner-only `app-push-<attempt>.outbox.json` using `writePrivate` with `{attempt,matched:1,outcome:'sent',completed:true,attempts:<actual count>}` only after those facts are observed. The runner does not receive operator database credentials. A provider-success outcome alone is insufficient; actual service-worker receipt is checked separately.

Finally, even after a failed send, the script restores A→B’s block first, cancels the captured request, revokes only the captured new subscription, restores A’s exact original notification preferences, and reads back both accounts’ block/connection/profile/device state. Restoring the original block removes the test notification and its outbox row through normal application behavior. The cancelled request metadata may remain under normal retention; no friendship is created. The restored block has a new creation timestamp, and ordinary directory/journal revisions advance; this restores relationship semantics, not a byte-identical database. It closes the notification, unsubscribes the browser, signs out both test sessions and verifies old cookies are denied, clears permission/cookies, closes Chrome, and deletes the exact fresh profile. A transport-ambiguous mutation keeps cleanup explicitly unconfirmed even if subsequent reads look correct, so the operator can reconcile it rather than assume a late commit cannot occur.

This procedure proves neither a visible OS banner nor production/iOS/closed-browser delivery. It preserves B’s recovery case and all original posts, keys, groups and relationships after the temporary block exception. No canonical build-status claim should change until a completed result and cleanup receipt exist.
