# Encrypted media and portable archives

POST /api/v1/media reserves a UUID, full encrypted envelope and byte count. The server validates the current recipient directory and stores only routing metadata plus SHA-256 of the canonical complete envelope in PostgreSQL. PUT /media/{id}/bytes must supply that exact full envelope as JSON bytes; a different context, recipient list, ciphertext or byte count is rejected before private R2 storage. R2 contains the full encrypted envelope once. Account quota reservations serialize on the member profile after the directory lock. The service never parses photo plaintext.

Post attachments match their post's audience, group and exact recipient list. Profile and group assets use PUT /media/{id}/attachment with kind, target_id and slot; the published profile/group envelope must match the media's parent and recipients. Only the profile owner or a current group manager can attach their own uploads. Each surface slot has one asset. Replacement/deletion enqueues durable private object deletion. Profile/group attachments survive abandoned-upload cleanup; individual deadlines still apply. Read authorization checks current relationship/group membership, blocks, historical recipient membership, and expiry.

Explicit removal is atomic with the new signed encrypted surface revision. PUT /profiles/me accepts optional `remove_media:[{id,slot}]` with up to three unique avatar/cover/background slots; PUT /groups/{id} accepts one image slot. The client removes the photo reference from its encrypted payload and submits the exact reviewed asset UUID. The database locks the target surface, checks current ownership or group management, rejects a different current asset with `409 MEDIA_ATTACHMENT_CHANGED`, and deletes the matching attachment in the same transaction as the envelope update. A missing asset is accepted only when the requested target slot is empty, allowing an expired photo's stale encrypted reference to be cleared. A stale envelope revision rolls back the deletion and outbox entry. Group managers can remove a previous editor's current image through this narrow operation without receiving general permission to delete that editor's uploads. Existing privacy-journal middleware covers both surface PUT routes; deletion and revision events are checkpointed before successful acknowledgement, and private object removal retries through the deletion outbox.

POST /exports creates a one-hour export job after recent authentication. GET /exports/{id} returns manifest discovery. Clients page with section=profile|posts|comments|post_reactions|comment_reactions|media|connections|groups and cursor. Each page has the named section, next_cursor and a stable generated_at. Profile is singular; other sections are arrays capped at 25 records. export_id is the validation cursor identity, with a target/tag composite for reactions. Server insertion timestamps distinguish new imports from their historical publication dates.

Exports contain the requesting person's own authored contributions, including their own historical group contributions; they never include a foreign parent post's body. Photo bytes use /exports/{job}/media/{id}/bytes under the same ownership/deadline checks. Clients decrypt locally and validate immediately before releasing a part through POST /exports/{id}/validate, with up to 1,000 kind/id/revision/expires_at references per request. Removal invalidates active jobs; revision/deadline changes fail validation. Cancelling a job immediately stops further reads.

Web and native archives use format porchday-archive, version 1, member/handle metadata, optional profile, authored entries, photo checksums, and minimal connection/group references. Each ZIP has archive.json, stable archive-part-NNN.json/index-part-NNN.html files, and its own subset of JPEG files. The final part includes a readable index. Multipart metadata has id/index/total:null until the final id/index/total:index/complete:true. Every part is required before import, even if an earlier part is readable by itself. Default encrypted parts use standard password-protected OpenPGP with one independent generated archive secret; encryption is never a proprietary archive cipher.

Archives preserve expiration metadata and provenance. Imports skip expired contributions, start private, re-encrypt with destination keys and validate photos before decoding. Comments/reactions become private journal entries because recreating unavailable foreign threads would falsely imply an original context or audience. User-saved copies remain outside the service's deletion control, which the export UI states explicitly.
