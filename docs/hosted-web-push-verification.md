# Real Web Push transport verification

On October 25, 2026 at approximately **18:40 UTC**, the single operator-authorized transport attempt `d8c37e2a` passed against Porchday's hosted staging service worker. `/health` afterward confirmed staging deployment **`39489d1d-b92a-4c48-b1a7-904c126bbbc3`**. No member signed in, no application subscription or notification row was created, and the existing synthetic-account browser profile was not used.

The check launched installed **Google Chrome 155.0.8059.85** in headless mode with a fresh, owner-only persistent test profile. Notification permission was granted only for the staging origin in that profile. Playwright's background-networking suppression flag was omitted for this process so provider connectivity was not deliberately disabled; HTTPS verification and application security headers remained intact. The user's browser/profile, permissions, accounts and OS configuration were unchanged.

The page used the real hosted service worker and `PushManager.subscribe`, with one newly generated VAPID key pair held only in memory. The actual subscription endpoint belonged to FCM. The existing application `webPushRequest` function produced one encrypted generic message and VAPID authorization, sent to that endpoint without following redirects. **FCM returned HTTP 201.** The check then observed an actual service-worker notification through `ServiceWorkerRegistration.getNotifications()`, matching title `Porchday`, body `You have a new update.`, and tag `porchday-update`. No synthetic push event, DevTools push injection, response mock or direct `showNotification` call was used by the check.

Cleanup closed the notification, unsubscribed and confirmed `getSubscription()` returned `null`, cleared the test-profile permission, closed the browser and deleted the newly created profile. The private result reports all cleanup steps complete. The ignored owner-only receipt stores a hash of the endpoint, not its capability URL or encryption material. VAPID keys, subscription keys and authorization headers were neither logged nor persisted by the harness.

This establishes **real provider-to-hosted-service-worker transport and notification creation** on this Mac. It does **not** establish the application's authenticated subscription-registration/outbox/cron path, production VAPID configuration, the operating system's visible banner, closed-browser delivery, iOS delivery, or long-term subscription renewal. The send used an ephemeral key pair, not production credentials. Provider acceptance alone would not have established receipt; the subsequent notification observation supplies that separate evidence. A later, separately authorized [application-level staging check](hosted-app-push-verification.md#observed-hosted-result) passed at 19:06 UTC using deployed staging VAPID, ordinary registration/event/cron and an independently observed sent outbox row; that later evidence does not expand the scope of this original transport attempt.

Before the send, separate empty-profile capability probes found secure-context service workers, PushManager, Notifications, `aes128gcm` support and no existing subscription in both Chrome for Testing 156.0.8078.4 and installed Chrome 155.0.8059.85. Those probes requested no permission and subscribed to nothing; their profiles were removed. API availability alone did not establish provider connectivity. The successful send above used installed Chrome only.

For application-level delivery, exercise an eligible notification event between separately authorized synthetic members, then observe both the real outbox's provider outcome and the receiving browser. `app.notify` intentionally skips notifications to the actor, so an A-only comment/reaction cannot generate this evidence. Account status must be checked independently: a pending stolen-account report is not evidence that B is held, and this transport check read or changed no account status or relationship. No test-only notification endpoint or SQL-inserted notification was added.

Standard Web Push with VAPID does not require a new Firebase project for this transport path. Chrome's protocol documentation distinguishes it from older proprietary GCM integration. [Chrome Web Push interoperability](https://developer.chrome.com/blog/web-push-interop-wins). Permission, a registered service worker and a real push-service subscription are separate prerequisites. [Chrome/web.dev subscription guide](https://web.dev/articles/push-notifications-subscribing-a-user). The test uses a dedicated profile because a test browser must not reuse personal browser state. [Playwright browser channels](https://playwright.dev/docs/browsers#google-chrome--microsoft-edge).
