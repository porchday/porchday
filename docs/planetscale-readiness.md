# PlanetScale Postgres provisioning review

Reviewed 2026-10-25 against migrations `000` through `037`, the existing migration/deployment scripts, current official documentation, installed `pscale` 0.348.0, and PlanetScale's public read-only pricing database. No paid PlanetScale resource was created during this review. `pscale size cluster list --engine postgresql --region us-west --format json` currently returns `NO_AUTH`; the linked Cloudflare billing account does not replace PlanetScale CLI authorization.

## Compatibility result

No unsupported SQL feature was identified. All 38 migrations applied successfully to a clean, disposable PostgreSQL 17.11 database under a role with `NOSUPERUSER CREATEDB CREATEROLE INHERIT LOGIN REPLICATION BYPASSRLS`, matching PlanetScale's documented default administrator attributes. The fixture used fresh, separately named runtime roles and left 42 RLS-enabled `app` tables. All three runtime roles were verified without superuser, BYPASSRLS, CREATEROLE, or CREATEDB. It did not install `pgcrypto`. The disposable database and test roles were removed afterward. This demonstrates ordinary non-superuser PostgreSQL compatibility, not a successful hosted PlanetScale migration.

The migrations use standard schemas, foreign keys/cascades, indexes, JSONB, SQL/PLpgSQL functions, triggers, transaction advisory locks, transaction-local settings, role grants, and row policies. The runtime roles remain `NOSUPERUSER NOBYPASSRLS` and do not own application tables. Privileged functions retain their restricted grants and pinned search paths. No server filesystem access, untrusted language, `COPY PROGRAM`, `ALTER SYSTEM`, custom C extension, or superuser-only trigger disabling is required by the migrations.

PlanetScale supports SQL-created roles, and its administrator is deliberately not a true superuser. Keep the stable schema/migration owner separate from application login roles. Owner-only restore checks depend on that operator having `CREATE` on `app`; runtime credentials must not have it. [PlanetScale roles](https://planetscale.com/docs/postgres/connecting/roles)

There is no `pgcrypto` dependency in the current migrations: UUID defaults use PostgreSQL's built-in `gen_random_uuid()`. PlanetScale nevertheless lists `pgcrypto` as supported if a later, reviewed migration needs it. Do not add it just to make provisioning look complete. [PostgreSQL UUID function](https://www.postgresql.org/docs/17/functions-uuid.html), [PlanetScale extensions](https://planetscale.com/docs/postgres/extensions)

Start with 10 GiB storage, baseline IOPS/throughput, and a reviewed storage growth ceiling such as 50 GiB. Enable capacity alerts before raising the ceiling. Keep photos in R2; do not store duplicate media ciphertext in Postgres. The $55/month base estimate excludes extra allocated storage, backup/WAL overage, egress, Cloudflare resources, support, and operator time. Use the PlanetScale CLI region slug `us-west`, which denotes AWS `us-west-2`; do not confuse its slug with the cloud region used in Worker placement. Set `--major-version 17` explicitly to match the tested version rather than relying on an evolving default. ARM architecture cannot be changed in-place later; choose it deliberately. ## Provisioning sequence and permissions

1. Restore authenticated `pscale` access, verify the intended organization and Cloudflare billing linkage, and query available Postgres sizes for `us-west`. Obtain the actual CLI SKU identifier from that response rather than guessing its casing or slug. Database create must specify `--engine postgresql`, the selected cluster size, `--replicas 2` for production or `0` for staging, and major version 17. `--cloudflare-billing @-` exists as a hidden flag in the installed CLI family. Pass Wrangler's signed billing payload over stdin, never a printed argument. [Cloudflare integrated creation](https://developers.cloudflare.com/hyperdrive/planetscale/), [CLI implementation](https://raw.githubusercontent.com/planetscale/cli/main/internal/cmd/database/create.go)
2. Create a stable migration/owner credential, run the migration ledger once through a direct verified-TLS connection, and retain its identity for future DDL/restore ownership. Do not use an ephemeral web-console identity as the schema owner. The current migration runner logs filenames only and fails without printing SQL or connection strings.
3. Create three provider-managed login credentials with `inherited_roles: []`, no replication privilege, and no arbitrary expiry, then grant only `porchday_auth`, `porchday_social`, or `porchday_jobs` respectively. Provider usernames include a branch suffix; SQL grants target the returned `base_username`, not the friendly display name. Confirm inherited permissions actually apply. Capture credential JSON directly into an exclusive mode-0600 file outside the repository; do not let `pscale role create --format json` reach terminal output. [Role API](https://planetscale.com/docs/api/reference/create_role), [role naming and SQL grants](https://planetscale.com/blog/one-postgres-cluster-many-apps)
4. Do **not** grant `pg_read_all_data`, `pg_write_all_data`, or `postgres` to runtime logins. The generic Cloudflare tutorial's broad read/write example is inappropriate here: it undermines the separate auth/jobs/social table grants. Use explicit-origin Hyperdrive configurations with the restricted credentials; integrated billing does not require accepting generic automatic runtime permissions. Keep one binding for each role and verify query caching is disabled on all three.
5. Prefer direct primary port 5432 as Hyperdrive's origin, because Hyperdrive already supplies transaction pooling. Use direct port 5432 for migrations, backups, and restore. If provider settings require port 6432, verify the additional transaction pool with the real role/context tests before using it. Never route authorization, expiry, or journal reads to an asynchronous read replica. Begin conservatively at five origin connections per Hyperdrive configuration and inspect total connection/memory headroom; the limit is soft and three bindings share the database budget. [PlanetScale connection methods](https://planetscale.com/docs/postgres/connecting), [Hyperdrive pooling](https://developers.cloudflare.com/hyperdrive/concepts/connection-pooling/)
6. Keep `pginsights.raw_queries=false` and verify the effective branch setting before any real identity data or credentials are queried. It otherwise captures literal values. Do not automatically enable `pg_strict` blocking for the restore operator: intentional global token/session invalidation uses bulk statements. Review each role's settings and test the exact restore workflow; a narrow transaction-local override is supported if the check is enabled. These settings do not replace RLS. [pginsights](https://planetscale.com/docs/postgres/extensions/pginsights), [pg_strict](https://planetscale.com/docs/postgres/extensions/pg_strict)

Before binding production, connect with **each actual runtime credential** and assert: no superuser/BYPASSRLS/CREATEROLE/CREATEDB; no table or function ownership; no `CREATE` on `public` or `app`; no inherited broad provider role; only its intended Porchday role. Exercise missing-member RLS denial, cross-member denial, auth table denial from social credentials, job function restrictions, commit/rollback context isolation, and recovery-journal owner-only rejection through the hosted bindings. Existing local tests are not a substitute for this check.

## Backup and restore requirements

PlanetScale includes 12-hour automatic backups, retained for two days, with WAL-based PITR through approximately five minutes before the present. Configure an additional daily backup retained seven days for **both production and staging**, matching the private media-snapshot lifetime; a default two-day staging policy cannot cover a retained seven-day media snapshot. Verify actual backup completion and retention before pilot admission. This supports the design's provisional 24-hour recovery-point target on paper; the eight-hour restore-time target still requires a timed hosted drill. [Backup policy](https://planetscale.com/docs/postgres/backups), [PITR](https://planetscale.com/docs/postgres/backups/point-in-time-recovery)

A seven-day retention policy does not imply that a newly created database already has seven days of history. Record the configured policy before enabling media snapshots, then check that each selected snapshot's exact paired database timestamp lies inside the provider's actual available PITR window before attempting a restore. A new database can complete a recent paired restore drill once that timestamp becomes recoverable; it need not wait seven days. The provisioning field `verified_pitr_days` and CLI option `--verified-pitr-days` record the verified retention policy, not an assertion about elapsed history.

A restored provider branch preserves managed-role object ownership but resets its passwords. SQL-created roles survive separately and do not appear on the provider Roles page. Reissue/verify runtime credentials and update all three Hyperdrive origins before release. Recheck required extensions on restored branches; provider documentation says extensions are not restored. Follow the independent-journal quarantine procedure before changing any database routing. Never use an older database backup to replace the R2 journal.

HA protects against individual instance/AZ failures; it is not a substitute for backups, and same-region backups do not establish cross-region disaster recovery. R2 ciphertext recovery is separate: the privacy journal contains deletion/access decisions, not a backup of photo bytes. Verify the restricted media backup/copy and deletion replay before claiming that the database-plus-media recovery plan is complete. No hosted restore, live role binding test, or real pilot capacity test has yet been completed under this review.
